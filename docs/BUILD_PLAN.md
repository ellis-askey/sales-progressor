# Sales Progressor Migration — Build Plan

The source of truth for **what's being remediated, in what order, and what the gate is for each phase**. Updated weekly as phases complete. Referenced by [CLAUDE.md](../CLAUDE.md) Laws section and [reference/COMPONENT_LIBRARY_CATALOG.md](reference/COMPONENT_LIBRARY_CATALOG.md).

This document is the answer to "what's next?" for the next ~6 months of remediation work, **interleaved with feature work** (locked at Phase 0 sign-off — no feature freeze).

---

## What this plan is

A phased migration to bring Sales Progressor to the discipline standard of the Cadence project (see comparison in this session's earlier responses). The plan is shaped by three constraints, in priority order:

1. **No regression.** Ever. Every change is a two-way door. See [Law 17 (behavioural baseline)](../CLAUDE.md#law-17--behavioural-baseline-before-remediation) and [Law 18 (visual + behavioural regression in CI)](../CLAUDE.md#law-18--visual--behavioral-regression-in-ci).
2. **Strangler pattern, not rewrite.** Every new line of code follows the new rules from day one of Phase 0. Old surfaces stay grandfathered until their turn in the queue. Nothing stops shipping.
3. **Highest-leverage surfaces first.** Customer-facing (portal) → high-touch agent surfaces (file detail, hub) → support and internal surfaces.

## Phase 1 — Inventory + Regression Harness (Weeks 2-3)

Two parallel tracks. You can't remediate what you can't see; you can't migrate safely without a regression net.

### Track A — Three censuses

A census per category. Each emits a markdown table and lives at [docs/inventory/](../inventory/).

| Census | Lives at | What it tracks |
|---|---|---|
| Components | `docs/inventory/COMPONENTS.md` | Every component, classified `canonical` / `to-extract` / `domain-specific` / `outlier-grandfathered` |
| Scripts | `docs/inventory/SCRIPTS.md` | Every script in `scripts/`, classified `archive-delete` / `promote-feature` / `promote-test` / `promote-npm-script` / `keep-as-is` |
| Surfaces | `docs/inventory/SURFACES.md` | Every route under `/agent`, `/portal`, `/dashboard`, `/command`. Scored on customer impact, frequency, current polish level (1-5), remediation complexity (S/M/L) |

Censuses are generated by scripts living at `scripts/inventory/*.ts` (registered in SCRIPTS_REGISTRY per Law 15 with `lifetime: ongoing`).

### Track B — Regression harness

The three layers from [Law 18](../CLAUDE.md#law-18--visual--behavioral-regression-in-ci):

1. **Visual regression** — Playwright `toHaveScreenshot()`. Initial coverage: the 9 existing canonical primitives, rendered in every state. Builds into the gallery in Phase 2.
2. **Behavioural regression** — Playwright happy-path E2E per high-priority surface. Initial coverage: 3 customer-facing flows (portal load, milestone confirm, completion banner). Expands per Phase 3.
3. **Multi-tenant safety regression** — automated test asserts every list endpoint goes through the access-scope helper. Catches the silent class of bugs where a refactor accidentally drops a `where` clause.

### Phase 1 acceptance gate

- All three census docs approved by founder.
- Regression harness running in CI on every PR (including initial visual / behavioural / multi-tenant tests).
- CI failing visibly on a test regression in a stub PR (proof the gate works).

**Gate not met:** Phase 2 does not start.

### Phase 1 risk profile

**Low.** Read-only censuses + new test files + CI config. No production code touched.

## Phase 2 — Canonical Primitives + Gallery (Weeks 4-9)

The Cadence "Phase 2 = library gate" equivalent. Adapted because we're consolidating existing patterns, not building from zero.

### Extraction order

Per [COMPONENT_LIBRARY_CATALOG §7](reference/COMPONENT_LIBRARY_CATALOG.md#7-migration-order-proposed-phase-2-sequence):

| Week | Primitive | Why this order |
|---|---|---|
| 4 | `Card` | Most-duplicated (56 + 15 = 71 instances). Unlocks every surface remediation |
| 5 | `Button` | High-frequency. 54 consumers. Mostly mechanical migration |
| 5-6 | `Banner` (extend AgentBanner) | Exists already; extend + migrate 12 consumers |
| 6 | `Pill` | Low risk. Light-touch. Consolidates 4 bespoke pill/chip patterns |
| 6-7 | `Modal` | 18 bespoke. Higher complexity (z-index, focus, scroll) |
| 7-8 | `Drawer` | 6 bespoke. Same complexity class as Modal |
| 8 | `Accordion` | Mechanical. 15 consumers |
| 8-9 | `Skeleton` + `Toast` | Light. Bundled |
| 9 | Gallery polish + acceptance gate | Founder review before Phase 3 |

### Per-primitive workflow

For each primitive, the same six-step loop:

1. **Build** primitive in `components/ui/` with the API sketched in COMPONENT_LIBRARY
2. **Document** it: add the full entry (props, variants, states) to COMPONENT_LIBRARY
3. **Gallery story** in `/dev/gallery/<primitive>` — render every state, desktop + mobile 375px
4. **Visual diff harness** — `toHaveScreenshot()` per state. CI must pass
5. **Migrate one real consumer** as proof. Visual diff before/after. Sign-off
6. **Mark all other bespoke versions** with `// canonical: components/ui/<Primitive> — migrate when next touched`

No primitive moves from "candidate" to "approved" without the gallery story being walked.

### `/dev/gallery` route

Built during Week 4 as scaffolding. Renders every approved primitive in every state. Gated to non-production environments via a feature flag.

The gallery is the **founder acceptance harness** — you walk it on desktop AND on a real phone, tick each primitive, and only then does Phase 3 begin.

### Phase 2 acceptance gate

- 8+ canonical primitives shipped to `components/ui/`
- Each documented in COMPONENT_LIBRARY with API + states
- Each rendered in `/dev/gallery` with visual regression in CI
- Each has at least one production consumer migrated as proof
- **Founder walks `/dev/gallery` on desktop and on mobile, ticks every primitive.** Synchronous sign-off — this is the big gate
- Visual regression CI catches an intentional pixel diff as a sanity check

**Gate not met:** Phase 3 does not start.

### Phase 2 risk profile

**Medium.** Each primitive is a new component, so adding it is safe. The risk is the proof-migration consumer breaking subtly. Mitigated by:
- API-as-superset rule (canonical primitive must support every behaviour of the bespoke it replaces)
- One consumer per primitive (per [Law 16](../CLAUDE.md#law-16--no-bulk-rewrites))
- Visual diff at pixel level
- Behavioural baseline + E2E test on the proof surface

## Phase 3 — Surface Remediation (Weeks 10-26)

Surface-by-surface remediation. The 11-surface queue from the earlier plan, refined.

### Surface queue (INTERNAL FIRST — locked Phase 0)

Order locked at Phase 0 sign-off: internal surfaces first (agent app for directors / negotiators, then internal dashboard for SP / admin), customer-facing portal last. Rationale: dogfood before exposing customer-facing changes. Each surface owns the 9-step review process below. Each ships behind a `CANONICAL_<SURFACE>_V2` feature flag for medium+ surfaces, default off, per-agency toggleable for staged rollout.

| Order | Surface | Routes | Audience | Rationale | Estimate |
|---|---|---|---|---|---|
| 1 | Agent file detail | `/agent/transactions/[id]` | director, negotiator (also viewed by SP, admin) | Where agents and SPs live daily. Highest-touch internal surface | 2 wks |
| 2 | Hub | `/agent/hub` | director, negotiator (SP / admin via internal-visibility resolver) | Daily landing for everyone except superadmin | 1 wk |
| 3 | Reminders | `/agent/reminders` | director, negotiator, SP, admin | Adjacent to daily work | 1 wk |
| 4 | Transaction list | `/agent/transactions` | director, negotiator, SP, admin | Every navigation touches it | 1 wk |
| 5 | To-Do | `/agent/to-do` | director, negotiator, SP, admin | Operational | 0.5 wk |
| 6 | Completions | `/agent/completions` | director, negotiator, SP, admin | Tied to revenue | 0.5 wk |
| 7 | Auto-emails | `/agent/auto-emails`, `/agent/transactions/[id]?tab=reminders` | director, negotiator, SP, admin | Touched a lot in recent sessions | 0.5 wk |
| 8 | Internal dashboard | `/dashboard` | SP, admin, superadmin | SP / admin landing — distinct from agent hub | 1 wk |
| 9 | Other agent admin | `/agent/account/*`, `/agent/admin`, `/agent/analytics`, `/agent/partners`, `/agent/my-files` | director, negotiator (mostly) | Lower urgency, bundled | 2 wks |
| 10 | Command Centre | `/command/*` | superadmin only | Founder-only. Low blast radius. Distinct visual system | 1 wk |
| 11 | Portal — buyer/seller | `/portal/[token]/*` | Customer (buyers, sellers) | **Last** per "internal first" decision. Highest-stakes (customer-facing, no second chance). Lock in the discipline internally before exposing to customers | 1 wk |

**Total surface time: ~12 weeks.** With 30-40% buffer for safety baseline + verification: **~17 weeks.**

### Per-surface workflow

For each surface, the same nine-step loop. Steps 1-3 are the audit; steps 4-9 are the work.

1. **Behavioural baseline doc** — every route fetched on load, every server action, every click handler, every email/push/DB side-effect, screenshots desktop + mobile 375px
2. **E2E happy-path test** — if it doesn't exist, write it first
3. **Audit doc** — what's missing per DEFINITION_OF_DONE: hover/focus/active/disabled, voice-pass, primitive coverage, loading/empty/error/first-time states
4. **Plain-English plan** — present to founder, wait for sign-off
5. **Implement** — replace bespoke components with canonical primitives, voice-pass strings, fix states, mobile pass
6. **Re-capture baseline** — diff against pre-work baseline, any unexplained diff is a regression
7. **Visual + behavioural regression CI** — must pass
8. **Feature flag** — surface lands behind `CANONICAL_<SURFACE>_V2`. Flipped per-agency for staged rollout
9. **Final report + screenshot** — founder sign-off, flag flipped for all agencies, surface marked DONE in this BUILD_PLAN

### Phase 3 acceptance per-surface

- All 11 surfaces complete the 9-step loop
- POLISH_TBD updated: items closed get moved to "Closed" section
- COMPONENT_LIBRARY updated: any new primitives that emerged from a surface get added
- Feature flags removed once stable

### Phase 3 risk profile

**Medium per surface, mitigated.** The flag mechanism is the safety valve — if a surface breaks for one agency, flip the flag, debug. The 9-step loop is the safety pattern. The feature-flag-per-agency rollout is the deployment pattern.

## Phase 4 — Scripts Cull (interleaved from Week 8)

Starts during Phase 2 (when bandwidth allows) and continues through Phase 3 as related surfaces close. Each surface remediation triggers a script-cull pass for its related scripts.

### Cull workflow

For each script in `scripts/`:

1. Audit `vercel.json`, `package.json`, CI workflows for references
2. `grep` repo + docs for the script name
3. Categorise per the Phase 1 census: `archive-delete` / `promote-feature` / `promote-test` / `promote-npm-script` / `keep-as-is`
4. For `archive-delete`: move to `scripts/_archive/` for 2 weeks. If nothing breaks, hard-delete
5. For `promote-feature`: build the admin action / route (under `/command/diagnose/*`)
6. For `promote-test`: write the Jest test, delete the script
7. For `promote-npm-script`: move to `package.json` scripts

### Phase 4 target

- `scripts/` ≤ 15 files
- All remaining scripts have entries in SCRIPTS_REGISTRY per [Law 15](../CLAUDE.md#law-15--scripts-must-justify)

### Phase 4 risk profile

**Low.** Soft-delete (2-week archive) catches anything referenced.

## Cross-cutting work happening in parallel

While Phases 0-5 progress, three streams continue:

### Feature development
The feature roadmap doesn't pause. From Phase 0 onwards, every new feature follows the new Laws. New components go in `components/ui/` if they're primitives; new domain components ship with COMPONENT_LIBRARY entries.

### Bug fixes
Bug fixes don't wait. They follow the existing process (PR, tsc, tests). They are NOT classified as Phase 3 remediation — that's a different scope.

### Founder sign-offs
The plan requires founder sign-off at 5 gates: Phase 0, Phase 1, Phase 2 (the big one — gallery), Phase 3 per-surface (11 surfaces), Phase 5. Asynchronous sign-off (screenshot + checklist in PR) is fine for most. Synchronous (call) reserved for Phase 2 gallery + 2-3 marquee Phase 3 surfaces (portal, file detail, hub).

## Acceptance criteria for "the migration is done"

The migration is complete when:

- All Laws enforced (mechanically where possible, by review otherwise)
- `components/ui/` is the source of truth; bespoke duplicates are migrated or grandfathered with documented reason
- `scripts/` ≤ 15 files, each justified in SCRIPTS_REGISTRY
- 11 priority surfaces complete the 9-step Phase 3 loop
- `/dev/gallery` renders every primitive in every state
- Visual + behavioural + multi-tenant regression covers every primitive and every Phase-3-completed surface
- POLISH_TBD has a healthy size (~30-80 entries, mostly `defer-Qx`) and is reviewed quarterly
- Zero LAWS-OVERRIDE entries in the last quarter (or all overrides are justified)
- A new contributor joining the codebase finds answers in docs, not in tribal knowledge

## Decisions locked at Phase 0 sign-off (2026-06-26)

- **Feature freeze:** none. Phases interleave with feature work.
- **Sign-off cadence:** synchronous for Phase 2 gallery gate AND for 3 marquee Phase 3 surfaces (agent file detail, hub, portal). Async (screenshot + checklist in PR) for the remaining 8 Phase 3 surfaces.
- **Phase 3 surface order:** internal first — agent app (director, negotiator, SP, admin views) before customer-facing portal. See surface queue above.
- **Phase 4 scripts target:** ≤ 15 files. Tight, forces real decisions per script.
- **Behavioural baseline (Law 17):** strict on every surface. No relaxed mode for internal-only.
- **Scripts law (Law 15):** strict. Registry entry + justification + deletion criteria for every new script.
- **Grandfather rule (Law 19):** kept as drafted. "Can't safely migrate" is a valid final answer.
- **Pill consolidation:** one primitive with variants. Locked in [COMPONENT_LIBRARY_CATALOG §9](reference/COMPONENT_LIBRARY_CATALOG.md#9-decisions-locked-at-phase-0-sign-off-2026-06-26).
