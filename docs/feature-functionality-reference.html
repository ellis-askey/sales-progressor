How to read this document

A capabilities inventory built by reading the salesprogressor codebase, not by paraphrasing the marketing site.

The vocabulary is the product's own. A piece of work in progress is a sale or a file, never a "transaction" (the code uses that word but the customers do not). The discrete pieces of progress on a sale are steps, never "milestones" (the code uses that word too). The product is Sales Progressor or the app, never a "platform".

Prices come from lib/billing/fee.ts. Sales Progressor is not VAT registered today, so every fee quoted is the actual headline price. Charging fires on exchange, not on completion.

Two callouts are used through the document:

  • SHIPS NOW The capability is live in the codebase at commit 3dea586.
  • PLANNED The schema or scaffolding exists but the capability is not yet wired through to users.
  • INTERNAL The capability is for Sales Progressor's own staff, not agents or clients.

The end of the document lists items the audit surfaced but could not fully confirm from the code. Treat that appendix as the to-do list for the next pass.

Part 1 - What each audience gets

Three audiences run through the product. Agents work in the full app; sellers and buyers experience it through the portal and the emails.

1.1 Agents

Agents are customer-agency staff: directors and negotiators at an estate agency that bought into the app. They sign in at portal.thesalesprogressor.co.uk and land in the agent app at /agent/*. The agent app is the full product surface.

The Hub SHIPS NOW

The agent's home page assembles a daily snapshot of the business. The strip across the top shows four pipeline-health figures:

  • Active files - count of sales in the active state.
  • Exchanging soon - sales whose expected exchange date falls in the next 30 days.
  • Need attention - the count of unique files with reminders that are due today, overdue, or escalated. The figure turns red when any reminder is escalated, amber otherwise.
  • Pipeline value - the sum of purchase prices across all active sales.

Beneath that strip, the hub renders:

  • A Needs your attention card listing up to three of the day's most urgent reminders.
  • A Coming up strip: how many sales are exchanging this week, completing this week, and the value closing this month.
  • A Stalled files warning: how many files have not seen a step completion in 14 or more days.
  • A Momentum ring showing pace versus the previous month.
  • An Exchange forecast showing exchange volume across the next four weeks.
  • A Service split donut: how many of the active files are self managed versus outsourced to the Sales Progressor team.
  • A Recent activity feed of the last few step confirmations.
  • A Diary showing today's expected exchanges and completions.
  • An Unassigned files widget for directors (files without an owner).
  • An Expired holds widget that surfaces on-hold files past their planned end date.

An empty-state variant appears when the agent has no active sales.

All Files / My Files SHIPS NOW

The same route renders one of two titles depending on visibility. Directors and admin see All Files across the agency; negotiators see My Files scoped to their own sales unless their director has flipped the canViewAllFiles flag. The list supports:

  • Status tabs: active, on hold, completed, withdrawn, draft.
  • Time-based filters: exchanging this week, completing this week, closing this month, exchanging in the next 30 days (the hub strip cards deep-link into these filters).
  • Free-text search across property address.
  • Columns: address, progress percentage, expected exchange date, owner, status.
  • An Exchange forecast month-pill strip across the top.
  • A New sale call to action.

The sale detail page SHIPS NOW

Every individual sale gets its own page at /agent/transactions/[id] with a header strip, a sidebar, and a tabbed body.

The header shows the property address, the agency, the sale status (active, on hold, completed, withdrawn), the tenure (freehold or leasehold), the purchase type (mortgage, cash buyer, cash from proceeds), and a service-type pill (Self managed or With progressor). Admins can click the service-type pill to flip a file mid-flight; the pill becomes interactive only for them. A back link returns to the file list.

The sidebar holds:

  • Purchase price, tenure, purchase type.
  • Predicted completion date.
  • Agent fee, referral fee, broker referral fee.
  • Key dates strip.
  • A file time tracker showing how many hours the agent and the progressor team have spent on this file.
  • The next step widget.
  • Exchange and completion status badges.

The body is tabbed:

  • Overview - contacts (vendor, purchaser, solicitors, broker), next step, active reminders, recent activity, the property chain, risk score, property intelligence, and internal notes.
  • Steps - vendor and purchaser step panels side by side. Each row shows the step's friendly name, status (complete, available, locked, not required), the date it was completed, grace days remaining if a reminder is attached, and a client-chase state chip if the system is chasing a client on this step.
  • Reminders - the list of reminder rules attached to this file, their due dates, status, snoozed state, chase task counts, and controls for marking done, snoozing, waking, or chasing. A pause toggle stops automated client emails for this file without affecting the agent reminder.
  • To-Do - manual tasks specific to this file, including "ask the progressor" requests from agents to the internal team.
  • Activity - a timeline of step completions, internal notes, contact edits, and automated email logs.

Reminders (the work queue) SHIPS NOW

The work queue is what an agent opens first thing in the morning. It groups the day's reminders by urgency:

  • Escalated in red - the system has chased the limit and not heard back.
  • Overdue in orange.
  • Due today in amber.
  • Coming up across the next few business days.

Each row shows the property address, the reminder name, the next due date, the count of times this has been chased, and a fallback-kind chip if the automated client chase could not run (for example the contact has no email on file, or the file has automated chases paused). From the row the agent can mark done, snooze, wake, or record a chase. A header strip shows stat pills (X overdue, Y due today, Z coming up).

Completions SHIPS NOW

After exchange a file leaves the day-to-day work queue and lives in Completions. The page groups exchanged files by completion urgency: overdue, this week, next week, later, no date set. Each row carries the address, completion date, purchase price, the fees billed on this file, and both solicitor firms. A summary line totals the file count, fees, and total sale value.

Updates SHIPS NOW

An app-wide feed of every step that has been confirmed. Grouped by day (Today, Yesterday, This week, Last week, and so on), then by file. Each row shows the date and time, the step name, the side (Sale or Purchase), who confirmed it, and a portal-confirmation badge when the client did the confirming. A filter toggle switches between "All steps" and "Client confirmations only".

Auto emails SHIPS NOW

A full feed of the automated client chase system. The page is scoped per role and shows four buckets:

  • Pending - emails queued to send.
  • Sent - the last 30 days of delivered chases.
  • Errored - sends that failed (bounced, no email on file, etc.).
  • Upcoming forecast - the next 14 days of expected chases.

For each row the agent sees the file, the email status, the recipient, the send time, and the error reason if any. Directors can scope to "mine only" or the whole agency.

To-Do SHIPS NOW

Manual tasks separated into:

  • My to-dos - tasks the agent has created for themselves.
  • With progressor / From agents - the cross-team request inbox. An agent on an outsourced file can flag a question to the progressor team and the progressor sees it here.
  • Overdue - the running list of things past their due date.

Partners SHIPS NOW

Two halves to one page:

  • Solicitor directory - every solicitor firm contacted on an active file, grouped by firm, with contact details, active file count, referral count, and chips to jump straight to the file.
  • Broker settings (director only) - preferred mortgage broker firm, contact, website, referral fee; plus a recommended-solicitors list with default referral fee fields.

Analytics SHIPS NOW

KPI cards (files created, exchanged, completed, completion rate, average time to exchange, average fees), an optional team-member filter for directors, and charts for monthly activity, KPI trends, files at risk (stalled 14 or more days), and referral income broken down by solicitor and broker.

New sale SHIPS NOW

A guided form at /agent/transactions/new-v2. The agent enters:

  • Property address.
  • Purchase price.
  • Tenure (freehold or leasehold).
  • Purchase type (mortgage, cash buyer, cash from proceeds).
  • Share of freehold flag.
  • Vendor and purchaser solicitor selections.
  • Mortgage broker (if applicable).
  • Service type (self managed or outsourced to Sales Progressor).
  • Notes.

If outsourced is picked the form adds an assignment step. The director-level billing gate blocks the form if the agency's trial has ended and no payment method is on file. Internal staff bypass this gate.

Account and notifications SHIPS NOW

At /agent/account/profile an agent can change their name, email, and email-notification preferences (weekly brief, chain notifications, and similar opt-outs).

Director-only surfaces SHIPS NOW

Directors get extra controls that negotiators do not see:

  • Billing at /agent/account/billing. Payment-method capture via Stripe, terms acceptance, the current month's running total, this month's trial savings, pending credits, and a history of issued invoices.
  • Automation settings at /agent/settings/automation. The master toggle that switches the automated client chase on or off for the agency, plus per-step grace days and repeat-every-days. Hard-coded ceilings of two chases maximum and 14 days of silence cap the engine.
  • Team management at /agent/account/team. Invite negotiators, manage their canViewAllFiles flag, resend or cancel pending invites.
  • Mortgage broker and recommended solicitors settings on the Partners page.

1.2 Sellers

Sellers (vendors in the code) do not get a full Sales Progressor account. They access the app two ways: through their portal link, and through the emails the app sends them.

What the seller portal gives them SHIPS NOW

The portal lives at /portal/[token]. The token is the seller's contact-level token (no password). It is mobile first, sized for a phone, and installable as a progressive web app.

Each row shows status (done, pending, not applicable), the friendly label, who is responsible (you, your solicitor, the agent), the typical duration, the date completed if done, and any event date that has been recorded. Actions a seller can take from the portal

  • Confirm a step. The portal shows a confirm button for steps that are available to the seller. The portal cannot confirm the six agent-only steps (VM18, PM25, VM19, PM26, VM20, PM27).
  • Set an expected date. When the agent does not yet know when a step will happen, the seller can supply one.
  • Leave a note. Free text addressed to the agent. Lands in the agent's notifications bell and on the file's activity feed.
  • Upload a survey report. Up to three files at a time, up to 10MB each, PDF/JPG/PNG/DOCX. Stored to the file in Supabase storage.
  • Explain an email. The seller can paste a confusing email from their solicitor and the app returns a four-section plain-English breakdown (what they are saying, what you need to do, deadlines, things to flag). Rate limited to three explanations per contact per hour.
  • Install the portal as a PWA. Web push opt-in is supported.
  • Unsubscribe. Every chase email carries an unsubscribe link. Clicking it stops chase emails and weekly updates but does not block the portal itself.

What sellers do NOT have

  • No login. Token in URL only.

1.3 Buyers

Buyers (purchasers in the code) use the same portal surface as sellers, with role-specific copy and a different set of steps. The differences are not cosmetic: the buyer's process is genuinely different.

How the buyer's portal differs SHIPS NOW

  • Language: "Your purchase of..." instead of "Your sale of...". Tips and checklists rewritten throughout.
  • Steps: the buyer follows PM1 through PM27 (27 steps), versus the seller's 20.
  • Mortgage-related steps: PM5 (mortgage application), PM6 (lender valuation), PM11 (mortgage offer) appear only for mortgage buyers. They auto-skip for cash buyers.
  • Searches: PM8 (orders searches) and PM13 (receives search results) are purchaser-only.
  • Survey: PM9 (book a Level 2 or 3 survey) is the only step in the whole system that the user can opt to mark as not required from the portal.
  • Deposit: PM24 (transfer the deposit) auto-skips when the buyer's deposit comes from a concurrent sale's equity (cash from proceeds).
  • Exchange and completion checklists are rewritten for the buyer: collect keys, take meter readings, buildings insurance, check items left, transferring the balance to the solicitor, broadband, change of address list, post redirect.
  • Post-completion guidance differs: the buyer is told about Land Registry, Stamp Duty, council tax setup, and confirming insurance is active.

What buyers receive by email

The same set as sellers, with buyer-specific copy. The portal invite, step confirmations, chase digests, weekly updates, exchange celebration, and completion survey are all sent to both sides where applicable. The chase digest tone branches on whether the buyer is being asked to do something themselves ("Yes this is done") or whether the system is nudging on something sitting with their solicitor or lender ("Yes this is already done").

2.2 Reminders and notifications

The reminder engine is the system that turns "files are happening" into "the agent has a single list of what to do today". It is a three-layer cascade:

  1. ReminderRule - configuration. There is one rule per chase scenario the founder has decided is worth chasing. Each rule has a grace-days value (how long after the anchor date before the first chase), a repeat-every-days value (how long between chases), an escalate-after-chases count, and a flag for whether it requires exchange-readiness.
  2. ReminderLog - per-file state. The engine creates one log row per applicable rule per active file. The log holds the next due date and the active/snoozed/completed status.
  3. ChaseTask - the agent's work item. When a log goes due, a task is spawned. The task is what the agent actually interacts with on the work queue.

How a reminder advances

  • The engine evaluates every active sale against every active rule each weekday morning at 06:00 UK.
  • For each rule, it resolves the anchor date (the completion date of the target step, or the file's creation date as a fallback).
  • First due date = anchor + grace days, normalised to 06:00 UK on that calendar day.
  • If the file is not yet exchange-ready and the rule requires it, the log stays dormant.
  • If the target step is already complete or not required, the log is deactivated.
  • When the agent records a chase, the log's next due date advances by the repeat-every-days value.
  • Once chase count crosses the escalate-after-chases threshold and the grace window has elapsed since the last chase, the row is flagged Escalated. The agent sees a red row.
  • The agent can snooze the row, mark it done, or wake it back up.

Where reminders surface

  • Hub - Needs your attention card. Up to three rows pulled by urgency.
  • Hub - Need attention pipeline stat. The count of unique files with actionable reminders.
  • Reminders page (work queue). The full list.
  • File detail Reminders tab. The reminders attached to one file.
  • File row badges. A staleness pill shows "Awaiting N days" on the file lists.

Automated client chase

When the work queue would otherwise spawn a manual task, the automated client chase tries to do the chase itself. The daily cron at 08:30 UK Mon-Sat groups due items per contact and sends one digest per contact. The chase tone branches on what the step is sitting on: "Yes this is done" for items the client has to do, "Yes this is already done" for items sitting with the solicitor or lender. If the chase cannot run (the contact has unsubscribed, has no email, has hit the max-chase cap, has been silent for over 14 days, has had emails paused, or has no portal token), the engine creates an agent fallback task instead with a labelled fallback-kind chip.

Notifications outside the reminder engine

  • In-app notifications bell. The internal staff dashboard has a bell that surfaces unread notifications. The confirmed type today is portal_milestone_confirm (a client confirmed a step from the portal). Other notification types fire too but the complete enum was not fully traced.
  • Push notifications. The portal supports web push via VAPID. The agent app exposes a push subscription mechanism but the live triggers were not exhaustively traced.
  • SendGrid event webhook. Delivery, deferral, and bounce events come back from SendGrid and are written against the originating queue rows.

2.3 The sale lifecycle and its steps

A sale moves through one of five states and is shaped by two orthogonal axes: service type (self managed or outsourced to Sales Progressor) and tenure plus purchase type (which determines which steps auto-skip).

The lifecycle states

StateWhat it meansWhat the system does
draftCreated but not yet submitted to the live processHidden from internal-staff search by default.

Auto-skip rules

What fires when a step is confirmed

Every step confirmation runs an atomic cascade:

  1. The step's direct dependents are unlocked.
  2. Any reminder logs targeting this step are auto-completed.
  3. The exchange gate (VM18 on the vendor side, PM25 on the purchaser side) is re-evaluated: if every blocking step on that side is now complete or not required, the gate unlocks.
  4. Any out-of-order completion flags downstream resolve themselves when their prerequisite chain catches up.
  5. The file's lastActivityAt is touched.
  6. An event row is written to the audit ledger.
  7. An email is enqueued to the other contacts on the file (single confirmation email, or a digest if more pile up inside three minutes).

The bilateral pairs

Four steps are bilateral: confirming one half of a pair confirms the other inside the same database transaction.

  • VM19 (exchange, vendor side) ↔ PM26 (exchange, purchaser side).
  • VM20 (completion, vendor side) ↔ PM27 (completion, purchaser side).

Exchange (the billing trigger)

VM19 or PM26 confirming sets exchangedAt on the file. If freeOnExchange is true (trial file), the engine stops there. Otherwise the file's purchase price is snapshotted into priceAtExchange and billedAtExchange is stamped. The snapshot is what the running total and the invoice line use from this point on. Subsequent price edits on the file do not change the fee.

Completion

VM20 or PM27 has no billing side effect (billing was already stamped at exchange). It fires a chain completion notification to claimed chain mates and, if every claimed link in the chain has now completed, enqueues a whole-chain celebration email (one per agent, guarded against duplicates).

Withdrawal and reversal

Setting the file's status to withdrawn records the optional fall-through reason, writes an internal note on the activity feed, and fires the chain withdrawal cascade (Lost buyer, Lost purchase, Asked to wait emails) if the file is chain-linked. Note: this does not reverse billing. If the file had already exchanged, the fee stays on the invoice.

If the agent instead undoes VM19 or PM26, the billing reversal helper fires. If the invoice is still in its "building" state for the current month, the file simply drops off it. If the invoice has already been issued, a credit note is written and applied to the next month's invoice.

2.4 The client portal

Full detail of what buyers and sellers see appears in sections 1.2 and 1.3. This section covers the portal as a system.

Authentication

Token in URL. Each Contact row carries a unique portalToken. Tokens persist indefinitely; there is no expiry or scheduled rotation in code. Tokens are generated by the agent from the file detail page via the generatePortalTokenAction server action; the token is then included in the portal invite email. There is no self-serve "re-request a portal link" mechanism for a contact; the agent has to regenerate.

Per-contact and per-token rate limiting

Portal-invite emails and explain-an-email calls are rate-limited per token to prevent abuse. The explain-an-email feature caps at three calls per contact per hour.

Document uploads

The Home page exposes an upload widget for the survey report. Submissions hit /api/portal/documents?token=.... Validation: PDF/JPG/PNG/DOCX, 10MB ceiling, up to three files per upload. Storage in Supabase at {transactionId}/{timestamp}-{random}.{ext}. A TransactionDocument row is created and a file_uploaded event is recorded. The portal itself does not let the user download what they uploaded; that surface is agent-only.

PWA and push

The portal has a Web App Manifest at /api/portal/manifest/[token] and supports the install prompt. Web push opt-in is supported via VAPID. The portal sets viewport: { maximumScale: 1, userScalable: false } and respects env(safe-area-inset-bottom) for notch clearance.

Unsubscribe

Every chase email carries an HMAC-signed unsubscribe link. Clicking sets the contact's unsubscribedAt timestamp. The portal stays accessible. The respond page renders an "opt-out" banner but still lets the contact confirm steps, set dates, or leave notes manually. There is no re-subscribe UI; the agent has to flip the flag.

2.5 Chain handling, invites, and claiming

Chain handling is one of the harder problems the app solves and one of the larger code surfaces.

The data model

A PropertyChain groups multiple ChainLink rows, one per position in the chain. Each link is either a stub (just an address and counter-party agent details, no real file behind it) or claimed (linked to a real PropertyTransaction). A file knows which chain link is its active one via chainLinkId.

Inviting the other agent

The originating agent adds a stub for the upward or downward neighbour and presses "invite". The system generates a token (7-day expiry on first send, 14 days on resend) and sends a chain invite email to the counter-party agent with two CTAs: Claim and Decline. The chain invite email lists the originator's agency, both property addresses, and the chain position.

Declining

Clicking Decline lands on a public page and writes back to the link without authentication. A decline notification fires to the originating agent.

Claiming

Clicking Claim lands on /claim. If the counter-party already has an account they sign in; if not they sign up via /claim/signup (which posts to /api/register with a claimSignup flag so the generic activation email is suppressed). After authentication the form posts to /api/claim with one of two actions:

  • create - a new sale is created on the counter-party's agency from the stub data.
  • link - an existing sale on the counter-party's agency is linked to the chain.

Either action verifies the user's email matches the stub email, asserts the new agency can create files (payment block check), stamps firstSubmissionAt if this is the agency's first sale, sets the link's transactionId, claimedByUserId, claimedAt, and flips the invite status to CLAIMED. The claim welcome email then fires - a property-aware welcome distinct from the generic activation email.

Reconciling history at claim

If the counter-party indicates "already in progress", they can retroactively mark steps as completed on the new file at the point of claim (e.g. "exchanged 3 days ago"). The reconciliation runs fire-and-forget after the main claim commits.

Step notifications across the chain

When VM19, PM26, VM20, or PM27 fires on any chain-linked file, the engine looks up every other CLAIMED link on the same chain (excluding the originating link) and enqueues a chain exchange or completion notification to each one. Recipients with suppressed addresses or per-user chain-email opt-outs are skipped. The deduplication key is (sourceId, recipient, emailType) so a duplicate notification cannot fire for the same chain event.

Withdrawal cascade

When a chain-linked file is withdrawn, cascadeChainWithdrawal queues:

  • Lost buyer to the nearest upward claimed mate.
  • Lost purchase to the nearest downward claimed mate.
  • Asked to wait if the chain is being reformed.

Recipients can respond with REMARKETING (will wait), WITHDRAW, or implicitly WAITING. If 14 days pass with no response, a single wait nudge fires. There is no further chasing after the nudge.

Whole-chain celebration

When every claimed link in the chain has reached completion, one celebration email goes to each claimed agent. Guarded by chain.celebrationSentAt so it cannot fire twice.

The trial

Any file that exchanges inside that 14-day window has its freeOnExchange flag set true at creation time and is exchanged without billing. The director's running total

The billing page at /agent/account/billing shows:

  • This month's metrics strip: total charges so far, exchange count, in-house versus outsourced split, lifetime trial savings, lifetime billed amount.
  • The current month's building invoice with line items (billed exchanges, trial exchanges marked free, pending credits). A "preview PDF" button renders the building invoice via the server-side PDF helper.
  • The history of past issued invoices with status (issued, paid, failed) and totals.
  • The payment-method panel, with the right action surfaced based on state: pending (terms not seeded), add card (acknowledged but no Stripe customer), card on file (Stripe customer attached).
  • Trial state and acknowledgement status.

The acknowledgement gate

Before the director can capture a payment method they must read and acknowledge the active terms version. The TermsVersion table holds the canonical commercial-terms document. The latest row with effectiveFrom ≤ now is the active version. The director's page renders a four-state machine for the payment-method panel:

  1. stripe_not_configured - the env vars are missing. Should not happen in production.
  2. pending - no terms version is seeded.
  3. disclosure - terms exist, the director has not yet clicked acknowledge.
  4. card_form - acknowledged, ready for Stripe card capture.

The acknowledgement audit row denormalises the user's name and email at the point of acknowledgement for GDPR robustness. When the founder publishes a new terms version with a later effectiveFrom, a fresh acknowledgement is required.

If VM19 or PM26 is undone after the file's invoice has been issued, a CreditNote is written for the full gross fee, marked as unapplied. An admin can flip a file from self managed to outsourced or back via the pill in the file's header. The action also clears the assigned progressor user when switching to self managed, sets progressedBy, and writes an internal note on the activity feed. Reminders, hub bucketing, and billing all read serviceType live, so the new behaviour applies from the moment of the switch.

Lifetime metrics

Lifetime totals shown on the billing page read from issued and paid invoice lines (history), not from a live recompute. Trial-savings totals are read from PropertyTransaction rows with freeOnExchange = true and exchangedAt set, computing what would have been charged via computeFee().

2.7 Accounts and access

Sign-up

An agency creates itself through one of three paths:

  • Self-serve password at /signup. The form posts to /api/register, which validates the inputs and calls createDirectorWithAgency, atomically creating the Agency row and the first User. Password is bcrypted before storage. The generic activation email is sent on success unless this is a claim signup.
  • Google OAuth via NextAuth. The Prisma adapter creates the user on first sign-in. The user is then routed to /signup/complete to fill in agency name and role.
  • Azure AD OAuth via NextAuth. Same flow as Google.

OAuth providers use allowDangerousEmailAccountLinking: true because both Google and Microsoft verify email ownership before issuing the token. The Account table links the OAuth identity to the User row.

Inviting team members

DirectionTriggerEmailExpiry
Director invites negotiatorDirector adds a negotiator on the team pageNegotiator invitation email with accept link7 days; resend extends
Negotiator invites directorOnly possible if the agency has no directorDirector invitation email with accept link7 days; resend extends

The invitee lands at /invite-negotiator/[token] or /invite/[token] and can accept via password or OAuth. Accept atomically creates the user, marks the invitation as accepted, and inherits the inviter's firmName. Both invitation models support cancel and resend.

Authentication

  • NextAuth with three providers: Credentials, Google, Azure AD.
  • JWT session strategy. The jwt callback populates user id, role, agencyId, firmName, and a needsSignupCompletion flag.
  • Credentials authorize is rate-limited per IP via checkAuthLimit.
  • Login success and failure events are written to the Event audit ledger with IP metadata.

Password reset

POST to /api/auth/forgot-password generates a 1-hour-expiry VerificationToken keyed on (email, token) and sends the reset email. The endpoint always returns 200 to avoid email enumeration. The reset link lands at /reset-password?token=...&email=... which posts to /api/auth/reset-password to apply the new bcrypted password and delete the token.

Multi-firm under one agency

Two soft-scoping fields control visibility:

  • firmName on User and Agency. Inherited from the director when a negotiator accepts an invitation. Currently only used in the chain invite email subject and a couple of display surfaces; does not drive file visibility.
  • canViewAllFiles on User. Set by directors on a per-negotiator basis. A negotiator with the flag set sees the full agency pipeline rather than just their own files. The flag is read by every list query and write guard.

Visibility by role

The canonical helper is lib/security/access-scope.ts. It returns one of three shapes:

  • all - admin and superadmin see every file across every agency.
  • assigned - sales progressor sees only files where assignedUserId matches.
  • agency - director and negotiator see files in their agency (negotiators further scoped to their own unless canViewAllFiles is set).

Audit ledger

Every meaningful action is written to the Event table via recordEvent. The helper is fire-and-forget so a logging failure cannot break the user action. EventType categories include auth events (login, password reset, invite, accept), agency events (created, mode changed, archived), transaction events (created, archived, status changed), step events (confirmed, marked not required, reversed, exchange gate unlocked, contracts exchanged, sale completed), comms events (chase sent, chase message generated, email parse attempted), file events (uploaded, deleted), feedback (submitted), and admin events (admin login, admin action performed).

Data retention

The data-retention cron runs every Sunday at 01:00. It anonymises non-superadmin users with updatedAt older than 3 years who have no active sessions and no active or on-hold sales. Email is replaced with anon-{id}@deleted.invalid, name is replaced with "Anonymised User", and personal fields (phone, password hash, TOTP secret) are nulled. A ?dryRun=true query parameter returns eligible users without writing.
