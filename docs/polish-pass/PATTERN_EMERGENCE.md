# Pattern Emergence — Polish Pass

Cross-page patterns discovered during Stage 1/2 inventory work. Each entry records when the pattern was first found, where it was documented, and how to apply it on subsequent pages.

---

| Pattern | First found | Documented in | Notes |
|---|---|---|---|
| Abstract skeleton ghost | completions Stage 2 | ANIMATION_STANDARDS.md §5 | No fake content (real addresses, task text). Only `agent-skeleton` bars at opacity 0.35, `pointerEvents: "none"`. Comms and completions polish pages use this. |
| Null-fallback omission | comms Stage 1 | comms inventory (A4) | Omit the element entirely rather than render a fallback word. Completions and comms precedent. Do not write "—" or "Unknown". |
| `agent-acc` for toggleable done/completed sections | completions Stage 2 | ANIMATION_STANDARDS.md §2 | `grid-template-rows: 0fr ↔ 1fr`, 200ms open / 150ms close. Completions UrgencyGroup, comms day-group, to-do done-section all use this. |
| Token-family adoption gap | to-do Stage 2 (2026-05-17) | POST_LAUNCH_FIXES.md | Components with hardcoded `#hex` or `rgba()` values that match existing semantic tokens (`--agent-info`, `--agent-danger`, etc.) but never got refactored. Risk: night-mode adds another patch for each unmigrated component. Mitigation: at Stage 2 of each page, grep the page's component tree for hardcoded colour values and check if they map to an existing token before writing new ones. |
| Empty state body redundancy | comms / completions / to-do Stage 3 (2026-05-17) | Pending documentation | Empty state bodies often duplicate orientation that surrounding UI elements already provide (form buttons, done toggles, parallel populated sections). Default test: if other UI elements visible in the empty state offer orientation, the body is likely redundant — drop it. Heading alone carries the state name; surrounding UI carries the next-action cue. Exception: global empty states with no other visible UI need a body for orientation. Note: this pattern applies retrospectively to comms "Completed milestones across your files will appear here." and completions "Once a file exchanges, it'll appear here." — but those are deployed and logged here for future audit reference only. Do not re-open those stages. |
| No floating labels above cards | to-do Stage 2 walkthrough (2026-05-17), surfaced from earlier comms + completions restructures | WORKFLOW.md (gate sub-step) | **Default rule:** any label that names or categorises a group of items must be inside or visually attached to a card surface — typically as a contained row or `agent-acc-hdr`. Free-floating uppercase labels above cards are the legacy pre-polish pattern. **SANCTIONED EXCEPTIONS (floating is allowed):** (1) Page-level title/subtitle in `PageHeader`. (2) Page-section headings that name navigation regions of a page containing multiple heterogeneous, independent cards (e.g. "My to-dos", "With your progressor"). Count badges adjacent to such headings inherit the same status. **NOT EXCEPTIONS (must be contained):** sub-group labels within a section (e.g. urgency-band labels like "Overdue", "This week"); category labels above a single card; any label whose subject is a single card or a homogeneous group of cards that could collapse into one container. **Test for the exception:** heterogeneous + independent + multiple cards = section-heading exception. Otherwise contain it. Stage 2 audits check this distinction explicitly when sweeping for floating labels. |
